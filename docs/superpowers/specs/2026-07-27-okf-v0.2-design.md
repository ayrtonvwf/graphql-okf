# OKF v0.2 by default, with in-place migration — design

Resolves [issue #9](https://github.com/ayrtonvwf/graphql-okf/issues/9).

Target: the [OKF v0.2 spec](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md),
published 2026-07-24, which supersedes the v0.1 spec `GOAL-M1` §5 currently
binds us to. Section numbers prefixed `§` refer to that spec; `GOAL-*` and
`NG-*` refer to `docs/northstar-specs/GOAL-M1.md`.

Builds on [issue #8](https://github.com/ayrtonvwf/graphql-okf/issues/8), which is
merged: the frontmatter parser is YAML-based and entry-oriented, and the root
`index.md` already declares `okf_version`. Both are prerequisites here.

## Goal

Emit v0.2 by default, keep v0.1 reachable behind `--okf-version 0.1`, and migrate
an existing v0.1 bundle in place — preserving each concept's original provenance
timestamp — when a v0.2 run finds one.

The move is not driven by conformance pressure. The reference tooling got
strictly *more* permissive in the migration (`REQUIRED_FRONTMATTER_KEYS` went
from four keys to `("type",)`), and our v0.1-form bundles parse and render today.
The argument is that v0.1 bundles are *accepted but not understood*: nothing in
the reference tooling reads `timestamp`, and the `mdcode` Dataplex round-trip
drops it entirely while carrying `generated`. `GOAL-M2-4.2` and `GOAL-M2-5.3` are
already specified in v0.2 field for field — adopting the vocabulary now stops M2
from reinventing it in a dialect nothing reads.

## Decisions

The four questions the issue left open, plus two the design raised, and the
calls made:

| Question | Decision |
| --- | --- |
| §2.3 `generated.by` value | `graphql-okf/<major.minor>` |
| §2.3 release churn | Exclude `generated` from the change comparison |
| §2.4.4 migration logging | A `**Migrated**` group; count only, no concept list |
| §2.5 downgrade | Error out |
| §2.6 `status: removed` | Namespace as `graphql_okf_status`; defer spec `status` to M2 |
| Version threading | An `EmitContext` record replacing the `timestamp` positional |

Out of scope, deliberately: `verified`, the §5.3 trust tiers, and `stale_after`
(§5.2–§5.5). Those are M2's provenance and staleness requirements and should be
adopted against real enrichment data, not emitted now as empty scaffolding.

## 1. Version selection

### 1.1 CLI

`--okf-version <0.1|0.2>`, defaulting to `0.2`. The flag joins the option list in
`src/cli.ts:19` and the usage string, following the existing `--out` / `--now` /
`--resource` style.

An unrecognised value throws
`GraphqlOkfError("INVALID_OKF_VERSION", …)` naming the supported set. It must not
fall back to the default silently — a typo that quietly writes the wrong dialect
is worse than a failed run.

### 1.2 Library

`okfVersion?: "0.1" | "0.2"` on `SyncOkfBundleOptions` (`src/index.ts:10-15`),
same default. A new `OkfVersion` type is exported from `src/index.ts` — the
single public entry point — so callers can name it.

### 1.3 `EmitContext`

`timestamp` is threaded today as a positional parameter through `buildBundle` →
`renderConceptParts` → `renderFrontmatter`. Adding a version alongside it would
make that three positionals deep and give M2 nowhere to put its own fields.
Instead, one frozen record, built once in `syncOkfBundle`:

```ts
export interface EmitContext {
  readonly okfVersion: OkfVersion;
  readonly timestamp: string;
  readonly producer: string; // "graphql-okf/0.1"
}
```

`buildBundle`, `renderConceptParts`, `renderConcept`, `renderFrontmatter`,
`renderTombstone` and `reconcile` take the context where they take `timestamp`
today. The change is mechanical at roughly six call sites.

### 1.4 Producer identity

`src/version.ts` exports `PRODUCER = "graphql-okf/0.1"` as a literal constant.
No runtime `package.json` read: the package ships dual ESM/CJS, and neither
`import.meta.url` nor `require.resolve` survives both build outputs cleanly, and
a filesystem read at emit time is a determinism hazard for no benefit.

A unit test reads `package.json` and asserts `PRODUCER` equals
`graphql-okf/<major>.<minor>`, so a release that forgets to bump the constant
fails CI rather than silently emitting a stale actor identity.

`<major.minor>` rather than the full patch version is a deliberate trade: it
follows the §7 `<producer>/<version>` convention closely enough to be readable by
a consumer classifying trust, while keeping patch releases entirely inert.

## 2. What changes in v0.2 output

§13.1 lists two breaking changes. One is a no-op for us.

### 2.1 `timestamp` → `generated`

Emitted at `src/emit/render/frontmatter.ts:22`:

| | v0.1 | v0.2 |
| --- | --- | --- |
| concept provenance | `timestamp: "2026-07-27T09:00:00.000Z"` | `generated: { by: "graphql-okf/0.1", at: "2026-07-27T09:00:00.000Z" }` |
| root `index.md` | `okf_version: "0.1"` | `okf_version: "0.2"` |

`generated` is written as a single-line flow mapping, matching the spec's own
example in §5.1. `generated.by` is required within the mapping; `generated.at`
is optional but always emitted.

### 2.2 `# Citations` → `sources`

A no-op: we emit neither. Worth recording for whoever picks up citation work —
the body heading is retired in v0.2 and `sources` frontmatter replaces it, so
that work should target `sources` directly and never emit the heading.

### 2.3 Tombstone status

`src/reconcile/tombstone.ts:29-32` emits `status: "removed"`. v0.2 §5.4 defines
`status` with a closed vocabulary — `draft | stable | deprecated`, absent meaning
`stable` — so this now overloads a spec key with an out-of-vocabulary value. The
visible consequence today is that tombstoned concepts render as unstyled badges
in the reference viewer, whose selector matches `status = "deprecated"`.

Decision: emit `graphql_okf_status: "removed"`, keep `removedAt`, and leave spec
`status` unset.

- Reusing `status: deprecated` would conflate "gone from the schema" with
  GraphQL's own `@deprecated`, which needs a home of its own. Keeping the
  distinction costs nothing now and M2 can decide how to surface both.
- The rename applies to **both** versions. v0.1 never defined `status` at all,
  so there is no reason to keep the overload alive on the legacy path.
- `isTombstoned` reads the new key **and** the legacy `status: removed`. Without
  the fallback, every tombstone written by an earlier release would stop being
  recognised and resurrect as an "added" concept on the next run.
- `graphql_okf_status` joins `MACHINE_KEYS` in `src/reconcile/frontmatter.ts:15`,
  so it is machine-owned and replaced rather than preserved as a human key.

Existing tombstone files are never re-rendered (a tombstoned concept is not in
the IR, so `buildBundle` never emits it), which means the legacy key persists in
old bundles indefinitely. The `isTombstoned` fallback is what makes that safe.

## 3. Change detection and release churn

`sameContent` (`src/reconcile/plan.ts:58-63`) compares rendered against existing
after stripping `timestamp`, via `withoutTimestamp`. That function is renamed
`withoutProvenance` and strips both `timestamp` and the whole `generated`
mapping.

The consequence: **a `generated`-only difference is never a change.** A concept
whose content did not change keeps the `by` and `at` of the run that actually
produced it, which is precisely what §5.1 asks `generated` to record — "how
current content was produced". A minor release is therefore a byte-identical
no-op across every existing bundle, and `log.md` stays free of thousands of
entries that differ only in a version string. Concepts still receive a fresh
`generated` whenever their content genuinely changes.

This is a rename of a mechanism that already exists, not a new special case in
the diff.

## 4. Migration

### 4.1 Shape: a pre-pass, not a render path

Migration is a frontmatter-level transform over the *existing* bundle text, run
before `reconcile`:

```
readExistingBundle → migrateBundle(existing, ctx) → reconcile(ir, migrated, ctx) → applyPlan
```

The alternative — migrating during rendering — does not work. Already-tombstoned
files are never re-rendered, so they would stay in v0.1 form forever and the
bundle would never finish converting, breaking both detection and the
idempotence guarantee. A pre-pass reaches every owned file uniformly.

`migrateBundle(existing, ctx)` returns the rewritten file map and the list of
paths it touched.

### 4.2 Per-file rules

For each owned file:

- **Preamble has `timestamp` and no `generated`** → replace that single entry
  with `generated: { by: <ctx.producer>, at: <the existing timestamp value> }`.
  The original timestamp is preserved verbatim. Restamping with the current time
  would destroy every concept's provenance in one run, which is the single worst
  outcome available here.
- **Root `index.md`** → `okf_version` set to `"0.2"`.
- **Neither marker** → left alone. A bundle with no markers anywhere is treated
  as v0.1 (§2.4.1); since there is nothing to rewrite, the two readings converge.

Everything else in the block — human-authored keys, comments, blank lines, key
order — is copied byte for byte. The entry-level parser from #8 exposes exact
source slices per entry, so this is a splice, not a re-serialisation. That is
what satisfies `GOAL-8.3`.

`generated.by` on a migrated concept is the *current* producer. We cannot know
which release originally wrote the file, and `by` is required within the mapping,
so this is the only honest value available. It warrants a one-line comment in
the code so the next reader does not mistake it for a bug.

### 4.3 Write actions

Migrated files are invisible to `sameContent` — `withoutProvenance` strips
exactly the region migration rewrites — so `reconcile` will report them as
unchanged and emit no action. `migrateBundle` therefore contributes its own
write actions for every file whose text it changed. Actions are deduplicated by
path with `reconcile`'s taking precedence, since `reconcile` starts from the
already-migrated text and is strictly newer.

### 4.4 Interruptibility (`GOAL-8.5`)

Detection is per file, never a bundle-level flag. A run killed mid-migration
leaves some files converted and some not; the next run migrates the remainder
and converges. The root index's `okf_version` flip is just another file in the
same set — a bundle whose index says `0.2` while some concepts still carry
`timestamp` is a recoverable state, not a corrupt one, precisely because
detection never consults the index alone.

The existing atomic-write path (`src/reconcile/apply.ts:9-14`) and log-first
ordering (`:25-30`) need no change.

### 4.5 Idempotence (`GOAL-8.1`, `GOAL-8.4`)

A second v0.2 run finds no file carrying `timestamp` without `generated`,
migrates nothing, produces no `**Migrated**` group and therefore no log entry,
and writes a byte-identical tree.

## 5. Downgrade

`--okf-version 0.1` against a bundle that declares or shows v0.2 form throws
`GraphqlOkfError("OKF_VERSION_DOWNGRADE", …)`, naming both versions and stating
that v0.2-only fields would be lost. The check runs before any work.

Detection for this purpose: root `okf_version` of `"0.2"`, or any concept
carrying `generated`.

Rationale: a silent backwards rewrite would discard any v0.2-only field
(`verified`, `stale_after`, `sources`) that a human or a future M2 run added.
If a genuine downgrade is ever wanted it should require its own explicit opt-in,
designed then.

## 6. Logging

`BundlePlan` gains `migrated: readonly string[]`. `hasLoggableChanges`
(`src/reconcile/log.ts:10-12`) counts it, so a migration-only run still produces
an entry.

`renderRunBlock` emits a new group above `Added`:

```markdown
### 09:00:00.000Z

**Migrated**

* OKF bundle format 0.1 → 0.2 (`timestamp` → `generated`) across 4975 concepts.

**Added**

* [`Order`](types/objects/Order.md)
```

- No concept list. Listing 5,000 paths under a heading is noise, not
  information; the count carries the fact and git carries the detail.
- Plain digits, no locale separators — locale-dependent formatting is a
  determinism hazard (`NG-6`).
- The count is of files whose provenance was rewritten (concepts and
  tombstones). The root index's version bump is implied by the line itself.
- Genuine schema-driven adds, changes and removes in the same run are still
  reported normally in their own groups.

## 7. Docs and tracked bundles

- `docs/northstar-specs/GOAL-M1.md:102` and `:262` are the only two places
  pinning v0.1. Reword to state the default (`0.2`) and the supported set.
  `GOAL-M2.md` names no version and needs no change.
- `GOAL-5.2` (`GOAL-M1.md:109-115`) names `timestamp` explicitly; reword for
  `generated`.
- README: document `--okf-version`, the default, and the migration behaviour.
- The tracked bundles under `okf/` and `examples/` are regenerated to v0.2 form,
  with the resulting migration log entry serving as the worked demonstration of
  the feature.

## 8. Testing

TDD per `CLAUDE.md`: failing test first, watch it fail, minimal code to pass. At
minimum:

- v0.2 output shape; v0.1 output unchanged under `--okf-version 0.1`
- unknown `--okf-version` value errors
- `PRODUCER` matches `package.json`'s `major.minor`
- migration: v0.1 fixture → v0.2, with `generated.at` equal to the original
  `timestamp` value, and human frontmatter keys and human prose surviving
  verbatim
- migration of an already-tombstoned file, and `isTombstoned` recognising both
  the new and the legacy status key
- migration produces exactly one log entry carrying the `**Migrated**` line,
  with schema changes in the same run still reported in their own groups
- re-run after migration: byte-identical tree, no new log entry
- interrupted migration: a half-converted fixture completes on re-run
- downgrade attempt errors
- a package-version bump alone produces no changes and no log entry
- determinism: same schema and same version flag → byte-identical bundle across
  runs

Coverage thresholds from `CLAUDE.md` apply: lines ≥ 90%, functions ≥ 90%,
branches ≥ 85%, statements ≥ 90%.
